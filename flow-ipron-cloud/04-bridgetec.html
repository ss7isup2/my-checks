Bridgetec 패키지는 다른 DB를 읽는 창입니다

com.wecoms24.bridgetec는 상담 내용을 저장하지 않습니다. 아이프론 클라우드(브리지텍)가 가진 상담사·조직·계정·STT 문장을 우리 API 모양으로 바꿔 프론트에 줍니다. 파일이 적고, Controller → Service → Mapper 세 칸이 그대로 보입니다.

왜 Flow CRUD를 안 쓰나

브리지텍 테이블은 우리 엔티티 규칙(entityId, TENANT_EID, ENTITY_STATUS)을 따르지 않습니다. 뷰 이름이 V_SAAS_APP_AGENT_INFO처럼 SaaS 스키마입니다. 그래서 JPA 엔티티로 매핑하지 않고, MyBatis가 SELECT 결과 컬럼을 Java 필드에 그대로 담습니다. 모델 클래스에는 @Entity가 없습니다. 조회용 객체입니다.

DB 연결이 갈라지는 지점

config/FlowBridgetecDataSourceConfig가 세 개의 빈을 만듭니다.

  1. DataSource — HikariCP. URL·계정은 FlowBridgetecDataSourceProperties가 프로퍼티에서 읽습니다. 풀 옵션(최대 연결, 타임아웃, readOnly)도 여기 있습니다.
  2. DataSourceTransactionManager — 이름 상수 BRIDGETEC_DB_TRANSACTION_MANAGER. Flow 본체의 flowMainTransactionManager와 다릅니다. 브리지텍 조회와 우리 티켓 저장은 한 트랜잭션으로 묶이지 않습니다.
  3. SqlSessionFactory — 이름 flowBridgetecSqlSessionFactory. XML 위치는 classpath*:mapper/bridgetec/*.xml.

@MapperScan(basePackages = "...bridgetec.mapper", sqlSessionFactoryRef = "flowBridgetecSqlSessionFactory") 때문에 BridgetecModelMapper 인터페이스의 메서드가 그 팩토리의 XML과 연결됩니다. 스캔 패키지를 빼먹으면 메서드를 호출해도 쿼리를 찾지 못합니다.

Mapper 한 장이 쿼리를 다 가집니다

인터페이스 bridgetec/mapper/BridgetecModelMapper.java와 XML src/main/resources/mapper/bridgetec/BridgetecModelMapper.xml의 namespace가 같습니다. 메서드 이름과 <select id="">가 같아야 합니다.

XML의 AGENT_ID as agentId처럼 별칭이 Java 필드 이름입니다. 별칭이 틀리면 필드는 null로 남고 예외는 안 납니다. 화면에서 내선이 비어 있으면 XML 별칭과 모델 필드를 먼저 비교합니다.

WHERE의 ACCOUNT_ID는 우리 Tenant.entityId가 아닐 수 있습니다. 소프트폰 로그인 서비스는 우리 테넌트를 TenantDao로 찾은 다음 tenant.getPortalAccountId()를 쿼리에 넘깁니다. 우리 PK와 포털 계정 id를 섞어 넣으면 상담사를 못 찾습니다.

서비스가 하는 얇은 일

Flow 서비스처럼 부모 클래스가 없습니다. @Service + 생성자 주입입니다.

BridgetecCounselorService.getBridgetecCounselorForSoftphoneLogin의 순서는 다음과 같습니다.

  1. 우리 DB TenantDao.findById(tenantId). 없으면 FlowException(NOT_FOUND_ENTITY).
  2. 그 테넌트의 포털 계정 id와 상담사 이름으로 매퍼 호출.
  3. 결과 BridgetecCounselor를 그대로 반환. 컨트롤러가 JSON으로 직렬화.

다른 조회 메서드는 매퍼 결과에 hasSubscribedAssistPremium 값을 실어 필드 하나를 더 채웁니다. 쿼리 두 번입니다. 목록 쿼리에는 프리미엄 컬럼이 없기 때문입니다.

조직·테넌트·STT·상태·전광판도 같은 패턴입니다. organization/factory, tenant/factory, counselor/factory는 조회 결과를 우리 화면 모델로 바꿀 때 쓰는 조립 클래스입니다. 쿼리 자체는 매퍼에만 있습니다.

프론트에서 부르는 위치

API 함수는 front/src/js/api/bridgetecApi.js에 모여 있습니다. 상담 화면이 주로 호출합니다. 소프트폰 컴포넌트(ipron/components/common/SoftPhone3.vue 등)가 로그인 시 상담사 내선을 받고, 상담 이력의 STT 팝업이 ucid로 문장을 가져옵니다. 관리 탭의 일반 CRUD는 이 매퍼를 거치지 않습니다.

수정할 때 손대는 파일 컬럼을 더 보여 주려면 모델 필드, Mapper 인터페이스 메서드(필요 시), XML SELECT, 그 값을 그리는 Vue를 같이 바꿉니다. 서비스는 매퍼를 통과만 시키는 경우가 많아서, 계산이 없으면 서비스를 안 고쳐도 됩니다. 우리 테넌트와 포털 계정을 섞는 로직이 있으면 서비스에 있습니다.
