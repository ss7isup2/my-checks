Controller, Service, DAO가 하는 일

Flow 업무 하나는 거의 항상 같은 7개 파일입니다. 공지사항(counsel/notice)이 가장 짧은 예시라, 그 파일을 기준으로 설명합니다.

한 업무의 파일 세트

파일역할공지 예시
Entity테이블 한 행. 컬럼과 필드.Notice.java / 테이블 NOTICE
SearchParameter검색 조건 + 저장할 본문.NoticeSearchParameter에 keyword
Dao 인터페이스저장소가 제공해야 하는 메서드 목록.NoticeDao
Dao 구현실제 쿼리. 추가 조건은 여기서.NoticeDaoImpl
Service 인터페이스업무가 밖에 보여주는 기능.NoticeService
Service 구현검증, 파일 첨부, 알림 같은 업무 규칙.NoticeServiceImpl
ControllerURL만 선언하는 경우가 많습니다.NoticeController는 본문이 비어 있습니다.

Controller는 URL과 “누구의 요청인지”만 담당

NoticeController는 부모만 상속합니다.

@RestController
@RequestMapping(FlowAppConstants.REST_API_NOTICE)  // /rest/api/v1/notice/notices
public class NoticeController extends BaseWebCrudController<
    User, JwtTokenProvider, Notice, Long,
    NoticeDao, NoticeSearchParameter, NoticeService> {
}

메서드는 부모 BaseWebCrudController에 있습니다. 제네릭 순서는 “사용자 타입, 토큰 제공자, 엔티티, ID 타입, DAO, 검색조건, 서비스”입니다. 이 순서가 맞아야 스프링이 entityService에 NoticeService를 넣습니다.

부모는 SecurityContextHolder에서 로그인 사용자를 꺼냅니다. JWT 필터가 미리 AuthUserDetails를 넣어 두기 때문입니다. 그래서 컨트롤러 메서드에 loginUser를 파라미터로 받지 않아도, 서비스 호출 직전에 getLoginUser()가 붙습니다.

부모가 만들어 주는 URL

기준 경로는 FlowAppConstants에 있습니다. 공지는 /rest/api/v1/notice/notices입니다.

메서드경로하는 일서비스 메서드
POST/한 건 등록. 본문은 SearchParameter.regist(user, entity)
POST/multiple여러 건 등록.regist(user, entities)
GET/조건에 맞는 목록.find
GET/?page&size다음 페이지 유무만 아는 조각(Slice).findSlice
GET/?page&size&isPaging총 건수가 있는 페이지(Page).findPaging
GET/totalCount건수만.findTotalCount
GET/{entityId}한 건.findOne
PUT/{entityId}한 건 수정. 경로의 id를 엔티티에 심음.update
PUT/multiple여러 건 수정.update
DELETE/{entityId}한 건 삭제.delete
DELETE/entityIds로 여러 건 삭제.delete
본문 모양이 엔티티 그 자체가 아닙니다 등록 JSON은 { "entity": { "title": "...", "content": "..." } }입니다. 컨트롤러가 searchParam.getEntity()를 서비스에 넘기기 때문입니다. 목록 조회는 쿼리스트링으로 entity.title, keyword, page, size, sort를 보냅니다. 공지 화면은 sort=createdDate,desc를 붙입니다.

JSON과 form-urlencoded를 둘 다 받도록 같은 경로가 두 번 선언되어 있습니다. 프론트 axios는 JSON을 씁니다.

응답 필드가 용도에 따라 달라지는 것은 @JsonView입니다. 목록용 뷰와 단건용 뷰가 나뉘어, 엔티티 필드에 뷰를 지정하면 그 뷰에서만 나갑니다. 공지의 작성자 이름은 목록·단건 둘 다 나가도록 ListEntityView와 SingleEntityView가 붙어 있습니다.

Service는 업무 규칙과 트랜잭션

인터페이스는 부모 인터페이스만 확장하는 경우가 많습니다.

public interface NoticeService extends BaseUserCrudEntityService<
    User, Notice, Long, NoticeDao, NoticeSearchParameter> {}

구현체는 AbstractBaseUserCrudEntityService를 상속합니다. 이 부모가 하는 일은 단순하고 중요합니다.

  • 조회·등록·수정·삭제 전에 entity.setTenant(loginUser.getTenant())로 로그인 사용자의 테넌트를 박습니다. 다른 고객사 행을 만들거나 고치지 못하게 하는 지점입니다.
  • 등록·수정·삭제는 @Transactional(transactionManager = "flowMainTransactionManager")입니다. 우리 DB 트랜잭션입니다.
  • 목록의 page, size, sort를 Spring PageRequest로 바꿉니다. 값이 없으면 0페이지, 20건입니다.

공지 구현체 NoticeServiceImpl은 부모 동작을 유지한 채 두 가지를 더합니다.

  1. 단건 조회 후 FileMetaDataDao로 resourceType = notice, resourceKey = 공지 ID인 첨부파일을 찾아 notice.files에 넣습니다. 첨부 테이블이 엔티티 연관이 아니라 리소스 키로 묶여 있다는 뜻입니다.
  2. FlowRedisMessageListener를 구현하고, 빈이 준비되면(afterPropertiesSet) Redis 구독자 목록에 자신을 등록합니다. Redis로 온 공지 메시지를 웹소켓으로 다시 보낼 수 있게 하려는 연결점입니다.

업무마다 다른 점은 ServiceImpl과 DaoImpl에만 있으면 됩니다. 공통 등록·수정은 부모를 그대로 호출합니다. 공지 등록은 return super.regist(loginUser, entity);입니다.

DAO는 쿼리. Flow는 JPA가 기본

“매퍼”를 찾을 때 src/main/resources/mapper부터 보면 공지·티켓 XML은 없습니다. XML은 두 개입니다.

  • mapper/bridgetec/BridgetecModelMapper.xml — 브리지텍 DB.
  • mapper/billing/BillingAccountMapper.xml — 빌링 계정.

나머지 업무의 DAO는 JPA입니다. 인터페이스는 BaseUserCrudEntityJpaDao를 확장하고, 구현은 AbstractBaseUserCrudEntityJpaDao를 상속합니다.

@Repository
@Primary
public class NoticeDaoImpl
    extends AbstractBaseUserCrudEntityJpaDao<User, Notice, Long, NoticeSearchParameter>
    implements NoticeDao {

  public NoticeDaoImpl(@Qualifier("jpaSharedEM_AWC_" + FlowAppConstants.MAIN_DB_ENTITY_MANAGER)
                       EntityManager entityManager) {
    super(Notice.class, NoticeSearchParameter.class, entityManager);
  }

  @Override
  protected void processAdditionalCriteria(...) {
    // keyword가 있으면 제목 OR 본문 LIKE
  }
}

생성자에서 EntityManager 이름을 지정하는 이유는 DataSource가 둘이기 때문입니다. 우리 DB용 엔티티 매니저를 골라야 합니다. @Primary는 같은 타입 빈이 여러 개일 때 이 구현을 기본으로 쓴다는 표시입니다.

부모 DAO가 엔티티 필드의 @SearchLike 같은 어노테이션을 보고 기본 WHERE를 만듭니다. 공지 제목에는 @SearchLike가 있어서, 검색 객체의 title이 채워지면 LIKE 조건이 됩니다. 제목과 본문을 한 키워드로 동시에 찾고 싶을 때만 processAdditionalCriteria를 재정의합니다. 공지는 keyword가 있으면 title 또는 rawContent에 LIKE를 겁니다.

템플릿에는 MyBatis용 부모 AbstractBaseCrudEntityMybatisDao도 있습니다. SqlSession.selectList(쿼리ID)로 find, findOne, insert를 호출하는 구조입니다. 새 업무를 XML로 만들고 싶을 때 이 부모를 쓸 수 있지만, 현재 도메인 DAO 구현은 JPA 쪽이 본체입니다.

Entity가 테이블이 되는 규칙

상속은 아래에서 위로 읽으면 됩니다.

BaseEntity
entityId
→
감사 필드
생성·수정자, 시각
→
TenantAwareBaseEntity
TENANT_EID
→
Notice, Ticket, …

TenantAwareBaseEntity는 @ManyToOne Tenant tenant를 TENANT_EID 컬럼으로 갖습니다. @TenantIsolation이 붙어 테넌트 필터 대상입니다. 테넌트 자신(Tenant)만 이 클래스를 상속하지 않고, 감사 필드 부모에 바로 붙습니다. 테넌트 행은 “어느 테넌트 소속”이 아니라 테넌트 그 자체이기 때문입니다.

필드컬럼의미
entityId업무마다 다름. 공지는 NOTICE_EID@AttributeOverride로 컬럼명을 바꿉니다.
createdBy / createdDateCREATE_BY, CREATE_DATEJPA Auditing이 채웁니다.
lastModifiedBy / lastModifiedDateMODIFIED_BY, MODIFIED_DATE수정 시 갱신.
entityStatusENTITY_STATUS물리 삭제 대신 상태. 검색 기본값은 삭제 상태를 빼는 쪽입니다. containDeleteStatusEntity로 포함 여부를 바꿉니다.
tenantTENANT_EID고객사.

공지에서 눈에 띄는 필드 기술은 세 가지입니다.

  • @Merge — 수정 시 이 필드를 기존 행에 합칩니다. 병합 유틸이 어노테이션을 보고 복사합니다. 없으면 수정 요청에 값이 있어도 반영되지 않을 수 있습니다.
  • @Formula — 조회 시점에 서브쿼리로 채우는 읽기 전용 값. 공지는 첨부 개수, 작성자 아이디·이름을 USER_TM에서 가져옵니다. 저장되는 컬럼이 아닙니다.
  • @Transient files — DB 컬럼이 아닙니다. 서비스가 조회 후에 채워서 JSON으로만 나갑니다.

전화번호 컬럼은 @Convert(converter = PhoneNumberConverter.class)로 DB에는 암호문, 애플리케이션에서는 평문입니다. 공지에는 없고 고객·티켓 쪽에 있습니다.

SearchParameter

public class NoticeSearchParameter extends BaseEntitySearchParameter<Notice, Long> {
  private String keyword;
  public NoticeSearchParameter() { super(Notice.class); }
}

부모 생성자가 Notice를 new해서 entity에 넣어 둡니다. 그래서 쿼리스트링 entity.title=안녕이 비어 있는 Notice의 title로 바인딩됩니다. 부모에 이미 있는 조건은 page, size, fromCreatedDate, toCreatedDate, entityIds, entities, sort입니다. sort 문자열은 createdDate,desc처럼 필드와 방향을 콤마로 잇고, 여러 개면 하이픈으로 잇습니다.

표준이 아닌 Controller

모든 컨트롤러가 CRUD 부모를 쓰지는 않습니다. 로그인은 토큰을 돌려줘야 해서 AuthController가 BaseWebController만 상속하고 POST /rest/api/v1/auth/login을 직접 선언합니다. 통계, 대시보드, 파일, 소프트폰, 외부 연동(SMS, 녹취, 아이프론 클라우드)도 조회·실행 API를 메서드로 직접 가집니다. “목록 화면이 있는 마스터 데이터”면 CRUD 부모, “동작 한 번”이면 메서드를 직접 쓴다고 보면 됩니다.

새 업무를 넣을 때의 순서

  1. FlowAppConstants에 REST_API_... 상수를 추가합니다.
  2. 엔티티를 TenantAwareBaseEntity<Long>으로 만들고, PK 컬럼을 @AttributeOverride로 지정합니다. 수정될 필드에 @Merge를 붙입니다.
  3. SearchParameter에 화면 검색 필드를 추가합니다.
  4. Dao 인터페이스 + DaoImpl. 추가 조건이 있으면 processAdditionalCriteria.
  5. Service 인터페이스 + ServiceImpl. 규칙이 없으면 super 호출만으로도 동작합니다.
  6. Controller는 경로와 제네릭만 채웁니다.
  7. 프론트 js/api에 같은 URL을 호출하는 함수를 만들고, 상담 화면이면 ipron/pages와 라우트, 관리 화면이면 pages/tabs와 menu.js 키를 연결합니다.
