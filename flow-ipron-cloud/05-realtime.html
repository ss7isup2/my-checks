스케줄러와 웹소켓

목록 새로고침으로 알 수 없는 일 — “지금 콜백이 배정됐다”, “예약 통화 5분 전이다”, “오늘 티켓이 몇 건이다” — 은 서버가 시간을 재서 계산하고, 붙어 있는 브라우저로 밀어 줍니다.

스케줄러는 그냥 스프링 빈입니다

FlowApplication의 @EnableScheduling이 켜져 있으면, @Component 안의 @Scheduled 메서드가 cron에 맞춰 호출됩니다. 별도의 스케줄러 서버 프로세스는 없습니다.

cron 여섯 칸은 초 분 시 일 월 요일입니다. 0 * * * * *는 “매분 0초”입니다.

클래스주기지금 도나하는 일
TicketBoardBroadcastScheduler
counsel/ticket/scheduler		 */10 * * * * *
10초마다		 예 오늘 00시~내일 00시 티켓 건수를 테넌트별로 구해 티켓 보드 토픽으로 보냅니다. 푸터의 티켓 카운트가 이 값을 받습니다.

counsel/ticket/callback/scheduler		 0 * * * * *
매분		 예. 마스터만 활성 테넌트 중 callbackAutoDistribution == true인 곳만 callbackService.autoDistributeCallbacks를 호출하고, 배정 결과를 웹소켓과 알림으로 보냅니다.

counsel/ticket/scheduler		 0 * * * * *

서버가 여러 대일 때 콜백 분배와 테넌트 해지는 com.wecoms24.flow.isMasterServer가 false이면 바로 return 합니다. 같은 작업을 인스턴스마다 돌리면 콜백이 두 번 배정되기 때문입니다. 통계·티켓 보드 스케줄러는 이 플래그를 보지 않습니다. 티켓 보드는 10초마다 “현재 건수”를 다시 보내는 성격이라, 중복 푸시가 데이터 변경은 아닙니다.

콜백 자동 분배가 하는 일, 순서대로

  1. 마스터 서버인지 확인합니다.
  2. tenantService.findAllActiveTenants()로 테넌트를 돌립니다.
  3. 테넌트의 자동 분배 설정이 켜져 있을 때만 autoDistributeCallbacks(tenantId)를 호출합니다.
  4. 배정된 콜백이 있으면 FlowWebSocketMessage로 감싸 Redis 발행 또는 SimpMessagingTemplate.convertAndSend를 합니다. 수신 타입은 USERS입니다. 배정 결과가 빈 목록이면 return이라, 뒤 테넌트는 이번 주기에 보지 않습니다.
  5. 같은 내용으로 Notification 행을 남겨, 사용자가 알림 목록에서도 보게 합니다.

예약 알림이 찾는 범위

TicketReservationBroadcastScheduler는 지금 시각부터 5분 뒤를 구간으로 잡고 예약 티켓을 조회합니다. 담당자 managerEntityId가 없으면 건너뜁니다. 메시지의 message 필드는 [재통화예약] 번호 {고객전화} 예약 통화 5분 전입니다. 형태입니다. 토픽은 /topic/ticket-reservation/{사용자아이디}입니다.

웹소켓은 STOMP입니다

설정 클래스는 core/websocket/WebSocketConfig입니다.

값상수의미
/wsWEBSOCKET_PATH브라우저가 여는 끝점. SockJS를 켭니다. 프론트 stores/websocket.js도 /ws로 SockJS를 만듭니다.
/flowWEBSOCKET_PREFIX_PATH클라이언트가 서버 메서드를 호출할 때 붙는 접두. @MessageMapping으로 들어옵니다.
/topic, /queue브로커 접두서버 → 브라우저 구독 주소. topic은 여러 명, queue는 개인 쪽으로 쓰는 관례입니다.

CONNECT 프레임에 Authorization 헤더가 있어야 합니다. 인터셉터가 Bearer 뒤 7글자를 잘라 JwtTokenProvider.getAuthentication(ACCESS, token)으로 사용자를 만들고, STOMP 세션 사용자로 넣습니다. 토큰이 없으면 연결이 깨집니다. 프론트는 연결 헤더에 X-Tenant-ID, X-Tenant-Subdomain도 같이 넣습니다.

메시지의 모양

오가는 JSON은 FlowWebSocketMessage 하나입니다. 업무마다 DTO를 새로 만들기보다, 공통 봉투에 내용을 넣습니다.

  • receiverType — USER, USERS, ALL_USERS. 한 명인지 여러 명인지.
  • receiver / receivers — 사용자 일부 필드(id, name, entityId).
  • className — 내용물의 원래 Java 클래스 이름. 프론트가 어떤 알림인지 구분할 때 씁니다.
  • jsonStringContent — 실제 데이터 JSON 문자열. 티켓 건수면 숫자 문자열, 예약이면 예약 객체 JSON.
  • message, title — 사람 눈에 보일 문장.
  • tenantId — Redis 채널 이름에서 구독자가 다시 채웁니다.
  • STT·채팅 전용 필드(sentence, callId, roomId 등)도 이 클래스에 함께 있습니다.

redisProperties.getBroadcaster().isEnable()이 켜져 있고 publisher가 있으면 Redis로 보냅니다. 꺼져 있으면 그 서버의 SimpMessagingTemplate으로만 보냅니다. 로컬 한 대면 후자만으로도 브라우저가 받습니다. 운영에서 인스턴스가 둘 이상이면, A에서 발생한 이벤트를 B에 붙은 사용자에게 전달하려면 Redis가 필요합니다.

채널 이름에는 테넌트 접두가 붙습니다. 예: {테넌트접두}{tenantId}:/topic/ticket-board. FlowRedisMessageSubscriber는 채널에서 테넌트 id를 떼어 FlowWebSocketMessage.tenantId에 넣고, 원래 토픽 이름으로 리스너에게 넘깁니다. 리스너 등록은 subscriber.addFlowRedisMessageListeners(this)입니다. 공지 서비스가 이 방식으로 자신을 등록합니다.

포털 계정 id로 된 채널이면 tenantService.findByPortalAccountId로 우리 테넌트 id를 다시 찾습니다. 브리지텍 쪽 식별자와 우리 TENANT_EID가 다르기 때문입니다.

테넌트 전용 메시지 매핑

tenant/websocket/TenantWebSocketController는 브라우저가 서버로 보내는 메시지용입니다. @MessageMapping 경로입니다.

  • /tenant/{tenantId}/message
  • /tenant/{tenantId}/user/{userId}
  • /tenant/{tenantId}/notification
  • /tenant/{tenantId}/status

실제 클라이언트 전송 경로는 애플리케이션 접두 때문에 /flow/tenant/{tenantId}/message입니다. 구독해서 받는 경로는 /topic/...입니다. “보내기”와 “받기” 주소가 다르다는 점만 구분하면 됩니다.

같은 패키지의 TenantWebSocketConfig와 TenantWebSocketInterceptor는 테넌트 채널에 대한 별도 브로커 설정과 입장 검사입니다. 앱 전체 STOMP 설정은 WebSocketConfig가 맡습니다.

프론트에서 연결이 열리는 곳

front/src/stores/websocket.js의 connect가 SockJS와 STOMP 클라이언트를 만듭니다. 이미 연결되어 있으면 다시 연결하지 않습니다. 성공 콜백에서 subscribe()로 토픽 목록을 겁니다. 상담 화면은 로그인 이후 이 스토어를 켜고, 알림 스토어·티켓 이벤트·STT 패널이 구독 콜백에서 상태를 바꿉니다.

디버그는 브라우저 개발자 도구 Network의 WS 프레임, 또는 서버 로그의 [FlowRedisMessageSubscriber] 한 줄을 보면 됩니다. 메시지가 Redis까지 갔는데 화면이 안 바뀌면 구독 토픽 문자열이 상수와 같은지, 사용자 id가 붙는 토픽인지 확인합니다.
